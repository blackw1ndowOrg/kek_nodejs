# Гуртки (Clubs)

Документація модуля гуртків: довідник гуртків із перевіркою кімнат і викладачів.

---

## 1. Огляд

- **Призначення:** CRUD гуртків (Музика, Англійська, Шахи, Малювання, Танці). Кожен гурток має **одну кімнату** типу `CLUB` і **одного викладача** типу `CLUB_TEACHER`.
- **Цілісність:** унікальність назви, «одна кімната — один гурток» і «один викладач — один гурток» гарантують унікальні індекси БД. Усе інше (тип кімнати, зайнятість групою, тип і статус викладача) перевіряє сервіс.
- **Видалення:** гурток видаляється разом зі своїми слотами розкладу в одній транзакції.
- **Контроль доступу (RBAC):** читання для `ADMIN`, `MANAGER`, `TEACHER`; зміни лише для `ADMIN`.
- **Помилки та валідація:** єдиний формат `{ error: { code, message, details? } }` і коди `VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `BAD_REQUEST` описані в `AUTH.md`. Тут вони не повторюються.

| Маршрут                        | ADMIN | MANAGER | TEACHER | PARENT |
| ------------------------------ | :---: | :-----: | :-----: | :----: |
| `GET /clubs`, `GET /clubs/:id` |  ✅   |   ✅    |   ✅    |   ❌   |
| `POST`, `PATCH`, `DELETE`      |  ✅   |   ❌    |   ❌    |   ❌   |

## 2. Компоненти та структура

### 2.1. Шари (`src/modules/clubs/`)

```
clubs.routes.js       auth → authorize → validate → controller
clubs.controller.js   req → сервіс → статус + JSON, без логіки
clubs.service.js      правила кімнати й викладача, переклад помилок БД
clubs.repository.js   єдине місце з Prisma, CLUB_SELECT
clubs.schema.js       Zod-схеми: id, створення, оновлення
```

Залежності передаються через конструктор (`new ClubsService(repository)`), тому в тестах репозиторій підміняється.

### 2.2. Правила сервісу

Перевірки йдуть у такому порядку; перша ж невдала зупиняє операцію.

| Крок     | Перевірка                          | Помилка |
| -------- | ---------------------------------- | ------- |
| Кімната  | існує                              | `404`   |
| Кімната  | тип `CLUB`                         | `400`   |
| Кімната  | не зайнята групою чи іншим гуртком | `409`   |
| Викладач | існує                              | `404`   |
| Викладач | тип `CLUB_TEACHER`                 | `400`   |
| Викладач | `isActive = true`                  | `400`   |
| Викладач | не веде інший гурток               | `409`   |

При `PATCH` кімната й викладач перевіряються **лише якщо справді змінюються**.

### 2.3. Помилки БД між перевіркою й записом

| Код Prisma | Результат                                                                  |
| ---------- | -------------------------------------------------------------------------- |
| `P2002`    | `409`; за `meta.target` визначається поле: `roomId`, `teacherId` або назва |
| `P2003`    | `404` (кімнату чи викладача видалили між перевіркою й записом)             |
| `P2025`    | `404` «Гурток не знайдено»                                                 |
| інші       | прокидаються як є (`500`)                                                  |

### 2.4. Видалення зі слотами

У `schema.prisma` зв'язок `ScheduleSlot.club` має `onDelete: SetNull`, тож без явного кроку в розкладі лишилися б заняття з `clubId = null`. Репозиторій у транзакції спершу виконує `scheduleSlot.deleteMany({ clubId })`, потім `club.delete`.

## 3. Ендпоінти API

Усі маршрути підключені за префіксом `/api/v1/clubs` і вимагають `Authorization: Bearer <TOKEN>`.

Об'єкт гуртка у відповідях:

```json
{
  "id": 4,
  "name": "Музика",
  "room": { "id": 6, "name": "Кабінет Музика", "type": "CLUB" },
  "teacher": { "id": 12, "fullName": "Ігор Лисенко" }
}
```

### 3.1. Список гуртків

- **URL:** `GET /api/v1/clubs`
- **Доступ:** `ADMIN`, `MANAGER`, `TEACHER`
- **Успішна відповідь (`200 OK`):** гуртки за зростанням `id`
  ```json
  {
    "clubs": [
      {
        "id": 4,
        "name": "Музика",
        "room": { "id": 6, "name": "Кабінет Музика", "type": "CLUB" },
        "teacher": { "id": 12, "fullName": "Ігор Лисенко" }
      }
    ]
  }
  ```

### 3.2. Один гурток

- **URL:** `GET /api/v1/clubs/:id`
- **Доступ:** `ADMIN`, `MANAGER`, `TEACHER`
- **Успішна відповідь (`200 OK`):** об'єкт гуртка
- **Помилки:** `400 VALIDATION_ERROR` (некоректний `id`), `404 NOT_FOUND`

### 3.3. Створення

- **URL:** `POST /api/v1/clubs`
- **Доступ:** `ADMIN`
- **Тіло запиту:**

  ```json
  { "name": "Шахи", "roomId": 7, "teacherId": 13 }
  ```

  | Поле        | Правило                                             |
  | ----------- | --------------------------------------------------- |
  | `name`      | рядок, пробіли по краях обрізаються, 1–100 символів |
  | `roomId`    | ціле число > 0                                      |
  | `teacherId` | ціле число > 0                                      |

  Інші поля заборонені.

- **Успішна відповідь (`201 Created`):** об'єкт гуртка
- **Помилки:**

  | Статус | Код                | Коли                                                               |
  | ------ | ------------------ | ------------------------------------------------------------------ |
  | `400`  | `VALIDATION_ERROR` | невалідне тіло                                                     |
  | `400`  | `BAD_REQUEST`      | кімната не типу `CLUB`; працівник не `CLUB_TEACHER` або звільнений |
  | `404`  | `NOT_FOUND`        | кімнати чи працівника не існує                                     |
  | `409`  | `CONFLICT`         | кімната зайнята; викладач уже веде гурток; назва вже існує         |

  Приклад:

  ```json
  { "error": { "code": "CONFLICT", "message": "Кімната вже зайнята групою або іншим гуртком" } }
  ```

### 3.4. Редагування

- **URL:** `PATCH /api/v1/clubs/:id`
- **Доступ:** `ADMIN`
- **Тіло запиту:** будь-яка комбінація `name`, `roomId`, `teacherId`, **мінімум одне поле**; зняти кімнату чи викладача (`null`) не можна.
  ```json
  { "teacherId": 14 }
  ```
- **Успішна відповідь (`200 OK`):** оновлений гурток
- **Помилки:** ті самі, що й при створенні, плюс `404`, якщо гуртка немає.

### 3.5. Видалення

- **URL:** `DELETE /api/v1/clubs/:id`
- **Доступ:** `ADMIN`
- **Успішна відповідь:** `204 No Content` без тіла. Слоти розкладу цього гуртка видаляються разом із ним.
- **Помилки:** `400 VALIDATION_ERROR`, `404 NOT_FOUND`

> Після видалення гуртка в розкладі груп з'являються порожні місця. Щоб перебудувати розклад, виконайте `POST /api/v1/schedule/generate` (див. `schedule-v1.md`).

## 4. Швидка перевірка через cURL

```bash
BASE=http://localhost:3000/api/v1

# 1. Токен адміна:
TOKEN=$(curl -s -X POST $BASE/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@kindergarten.local","password":"Admin123!"}' | jq -r '.token')

# 2. Список гуртків:
curl -s -H "Authorization: Bearer $TOKEN" $BASE/clubs | jq

# 3. Створення (потрібні ВІЛЬНА кімната типу CLUB і ВІЛЬНИЙ викладач CLUB_TEACHER):
curl -s -X POST $BASE/clubs \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"Робототехніка","roomId":<ROOM_ID>,"teacherId":<TEACHER_ID>}'

# 4. Видалення:
curl -s -X DELETE -H "Authorization: Bearer $TOKEN" $BASE/clubs/<CLUB_ID> -w "%{http_code}\n"
```

Після `npm run db:seed` усі 5 кімнат `CLUB` і 5 викладачів уже зайняті гуртками, тому для створення нового спершу потрібні нова кімната (`POST /rooms`) і новий працівник.

## 6. Обмеження v1

- Перевірки кімнати й викладача та запис виконуються окремими запитами без спільної транзакції. При одночасних запитах спрацьовують унікальні індекси БД (`409`).
- Один гурток має рівно одного викладача й одну кімнату (так влаштована схема).
